# v0.4.0 Benchmark 报告 —— 代码生成的成本

生成时间：见 `results.json`。

## 为什么这样设计

v0.1~v0.3 测的都是**运行时**（请求吞吐、上下文开销），这一版不一样：
代码生成发生在**开发期**，真正的指标是「契约改一行，我要等多久」。

- 小于 ~50ms：可以挂 watch，边改边生成，开发者无感
- 几百毫秒：能接受，但不会频繁跑
- 大于 1s：开发者会开始"攒着一起改"，契约从此与代码脱节

所以这份报告的核心数字是 **端到端 30.7ms**，而不是解析吞吐。

## 契约样本

12 个 service × 3 条路由（1 个纯查询、1 个带 body、1 个带路径参数）+ 36 个 DTO。
共 312 行契约。

## 结果

| 阶段 | 平均 | 吞吐 | p95 |
| --- | --- | --- | --- |
| 解析 `.api` | 0.43 ms | 2,304 ops/sec | 0.75 ms |
| 解析 `.api.ts` | 0.57 ms | 1,768 ops/sec | 0.87 ms |
| 生成（来自 `.api`） | 1.69 ms | 592 ops/sec | — |
| 生成（来自 `.api.ts`） | 1.49 ms | 673 ops/sec | — |
| **端到端（解析+生成+写盘）** | **30.7 ms** | — | 31.6 ms |

### 杠杆率

312 行契约 → 1,076 行代码 / 73 个文件（**3.45×**）。

## 怎么读这些数字

1. **解析比生成快 3~4 倍** —— 手写扫描器 + 递归下降的收益。
   没有 ANTLR 生成的状态机，也没有正则回溯的风险。

2. **端到端的 30.7ms 里，绝大部分是写盘**（73 个文件的 `mkdir` + `writeFile`）。
   纯计算只有约 2.1ms。也就是说：
   - 想更快，先做「内容相同就不写」（`writer.ts` 已经这么做了，见下）
   - 而不是去优化解析器

3. **幂等 = 二次生成几乎免费**。示例项目第二次执行：

   ```
   ✓ 0 file(s) into .../src
   ```

   内容没变就不落盘。这让 `watch` 模式下的重复触发成本接近零，
   也是我们把「内容比较」放在写入前的唯一理由。

## 与运行时的关系

这一版**没有新增请求路径上的开销**：生成产物是普通的手写风格 TypeScript，
运行时代价和 v0.3.0 的同等代码一致（30~35%，见 v0.3.0 报告）。
代码生成是**编译期**的能力，不该进请求链路。

## 复现

```bash
pnpm bench v0.4.0 --iterations=300 --report
```

## 已知限制

- 端到端样本量较小（默认 `iterations/10`），因为每次都要建临时目录
- 未测量模板覆盖目录存在时的额外 IO（预期增加 <1ms）
- 生成的行数统计包含注释与空行，杠杆率因此偏保守
