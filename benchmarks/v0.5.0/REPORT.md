# v0.5.0 Benchmark 报告 —— 数据访问与缓存

生成时间：见 `results.json`（`--iterations=800`）。

## A. ORM（内存数据源）

| 操作 | 平均 | 吞吐 | p95 |
| --- | --- | --- | --- |
| insert | ~0.005 ms | 210,719 ops/sec | 0.01 ms |
| findById | 0.07 ms | 13,346 ops/sec | 0.24 ms |
| query（where + order + limit） | 0.22 ms | 4,599 ops/sec | 0.40 ms |
| paginate | 0.08 ms | 12,295 ops/sec | 0.22 ms |
| transaction（提交） | 0.06 ms | 15,970 ops/sec | 0.09 ms |

**怎么读**：内存数据源下 ORM 的额外开销在 **0.01~0.2ms** 量级。
对比 v0.2.0 测得的整条 HTTP 链路（约 0.5ms 级），ORM 不是瓶颈；
真正决定性能的是后面的数据库，这里测的是**框架自身的厚度**。

值得注意的是 `query` 比 `findById` 慢 3 倍：条件求值 + 排序 + 切片都在内存里逐行走。
在内存实现里这是可接受的；换成 SQL 数据源后，这些工作由数据库承担，
所以**不要**照着这个数字推断真实数据库下的表现。

## B. 缓存

回源统一带 **1ms 模拟延迟**（否则两边都是 0ms，量不出东西）：

| 场景 | 平均 | 吞吐 |
| --- | --- | --- |
| 命中 | ~0.001 ms | 815,179 ops/sec |
| 纯回源（NullCache） | 1.23 ms | 810 ops/sec |

**加速比 ≈ 12,300×**。这个数字没有物理意义（分母是人为的 1ms），
它的意义在于量级：**命中与回源差三到四个数量级**，
所以"能不能命中"才是缓存设计里唯一重要的问题。

### 击穿保护

同一 key 并发 50 次：

```
回源次数：1
总耗时：0.22 ms
```

50 个并发请求只打了一次数据库——这就是 `getOrSet` 的价值。
如果业务代码自己写 `get → 未命中 → 查库 → set`，这里会是 50 次。

## C. 迁移

20 条迁移共 4.78 ms（单条 0.24 ms）。开销可以忽略，
所以**迁移应当经常跑**：它比"手工改表 + 口头通知"可靠得多。

## 复现

```bash
pnpm bench v0.5.0 --iterations=800 --report
```

## 已知限制

- 全部基于内存数据源；SQL 数据源的开销取决于驱动与网络，未测
- 缓存加速比的分母是人为延迟，只看量级
- 未测 LRU 淘汰在大数据量下的成本（淘汰是 O(n log n) 排序，max 很大时会痛）
