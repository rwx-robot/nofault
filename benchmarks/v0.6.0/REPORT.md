# v0.6.0 Benchmark 报告 —— RPC

生成时间：见 `results.json`（`--iterations=2000 --concurrency=50`，本机 socket）。

## 结果

| 场景 | 数值 |
| --- | --- |
| 串行调用（连接已就绪） | 0.16 ms / 6,134 ops/sec（p95 0.27 ms） |
| 每次新建客户端（含建连） | 0.50 ms |
| 池化收益 | 省 0.34 ms/次，约 **3.1×** |
| 50 并发 × 40 次 | 2,000 次共 63.3 ms，**31,590 ops/sec** |
| 连接池实际大小 | 1 |

## 怎么读

1. **RPC 自身开销 0.16ms** —— 对比 v0.2.0 测得的 HTTP 全链路（约 0.5ms 级），
   RPC 比 HTTP 便宜约 3 倍，主要省在 HTTP 头部解析与中间件链。

2. **池化省 3.1×** —— 建一次 TCP 连接要 0.34ms。
   这个数字在真实网络（跨机、跨机房）会大到 1~2 个数量级，
   所以**连接池不是优化，是必需品**。

3. **50 并发只用 1 条连接**，吞吐 31,590 ops/sec ——
   一条连接上可以同时有多个在途调用（靠 `id` 配对响应），
   这正是"为什么请求要有 id"的答案：没有 id，一条连接就只能串行，
   要么退化成"一调用一连接"（池被打爆）。

## 复现

```bash
pnpm bench v0.6.0 --iterations=2000 --concurrency=50 --report
```

## 已知限制

- 本机回环，不含真实网络延迟与丢包
- JSON 编解码开销已计入，但未与二进制协议（protobuf / msgpack）对比
- 未测大 payload（>1MB）下的分帧与背压行为

## 一个被数字掩盖的事实

串行 6,134 ops/sec 看着不高，是因为**每次调用都等前一个返回**。
真实服务里调用是并发的（见 C 的 31,590 ops/sec），
所以评估 RPC 性能时，**并发吞吐才是有效指标，串行延迟只反映单请求体验**。
