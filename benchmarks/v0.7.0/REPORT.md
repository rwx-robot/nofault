# v0.7.0 Benchmark 报告 —— 治理原语的成本

生成时间：见 `results.json`（`--iterations=50000`）。

## 结果

| 原语 | 单次开销 | 吞吐 | p95 |
| --- | --- | --- | --- |
| 令牌桶判定 | 0.22 µs | 4,542,152 ops/sec | 0.39 µs |
| 按 key 限流判定 | 0.48 µs | 2,099,077 ops/sec | 0.58 µs |
| 熔断器状态判定 | 0.10 µs | 10,299,616 ops/sec | 0.17 µs |
| 舱壁计数 | 0.10 µs | 9,685,042 ops/sec | 0.21 µs |
| 退避计算 | 0.24 µs | 4,116,965 ops/sec | 0.49 µs |

## 怎么读这些数字

**都在 1 微秒以内**。这是硬性要求：治理逻辑在每条请求上都要跑，
对比 v0.2.0 测得的一整条 HTTP 链路（约 0.5ms = 500µs），
治理的总开销不到 **0.2%**。

换句话说：**没有理由因为"怕影响性能"而不加熔断限流**。
真正会拖慢系统的是"不加保护，让一个慢依赖拖死整个服务"。

几个值得注意的点：

1. **按 key 比单桶贵一倍** —— 多出来的是 Map 查找。
   仍然只有 0.48µs，可以接受
2. **熔断判定最便宜（0.1µs）** —— 闭合状态下只是一次状态读取，
   没有定时器、没有锁。"冷却到期转半开"是惰性判断的（读的时候才算）
3. **退避计算 0.24µs** —— 抖动用的是 `Math.random()`，
   在重试路径上这点开销可以忽略

## 复现

```bash
pnpm bench v0.7.0 --iterations=50000 --report
```

## 已知限制

- 测的是纯判定开销，不含 I/O 与网络
- `Bulkhead.run()` 的等待路径（队列轮询 1ms 粒度）未测：
  它只在高负载时才会走到，且等待时间远大于判定时间
- 多进程/分布式限流需要外部存储（如 Redis），本版未实现
