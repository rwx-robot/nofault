# v0.8.0 Benchmark 报告 —— 可观测性的成本

生成时间：见 `results.json`（`--iterations=20000`）。

## 结果

| 操作 | 单次开销 | 吞吐 | p95 |
| --- | --- | --- | --- |
| 起一个 Span 并结束 | 5.84 µs | 171,362 ops/sec | 7.49 µs |
| 不采样时（直接返回 null） | 0.27 µs | 3,688,153 ops/sec | 0.24 µs |
| Span + 4 个属性 | 5.62 µs | 178,023 ops/sec | 7.18 µs |
| Counter 自增 | 1.06 µs | 940,453 ops/sec | 1.14 µs |
| Histogram 观测 | 0.85 µs | 1,173,072 ops/sec | 0.98 µs |
| Prometheus 序列化（500 序列） | 880 µs | 1,136 ops/sec | 1,154 µs |

## 一个中途发现并修掉的性能问题

初版 Span 开销是 **13.93 µs**，比指标（1µs 量级）贵一个数量级。
拆开量下来，绝大部分花在 **ID 生成**上：

| 步骤 | 开销 |
| --- | --- |
| `crypto.getRandomValues(16)` | 2.93 µs |
| `new Uint8Array(16)` + 填充 | 4.18 µs |
| `toString(16).padStart(2,'0')` 拼 32 字符 | 5.84 µs |

两处改完降到 5.84 µs（**2.4×**）：

1. **十六进制查表** —— `padStart` 每个字节都要分配一次临时字符串，256 项的表直接查
2. **一次随机填充产出 traceId + spanId** —— 24 字节一次填完，比 16+8 两次填省一半

> 这个优化值得记下来，是因为它说明了**可观测性的成本常常不在"埋点"本身，
> 而在你顺手写下的那些"看起来很便宜"的辅助操作**。

## 怎么读这些数字

1. **不采样 = 0.27µs**（约 21 倍差距）—— 这就是"采样在创建时决定"的意义。
   如果先建 Span 再丢弃，你为每个被丢掉的 Span 付了 5.84µs，
   采样率再低也省不下来

2. **Span 比指标贵 5 倍**（5.84µs vs 1.06µs）—— 所以**高频循环里只该加指标，
   不该起 Span**。判断标准很简单：这个调用我会不会想看它的耗时分布？不会就别埋 Span

3. **序列化 880µs 但只在抓取时发生** —— Prometheus 每 15s 抓一次，
   880µs 完全无所谓；**不要为了这个数字去牺牲埋点的完整性**

4. **对比 v0.2.0 的 HTTP 全链路（约 500µs）**：一个请求起 3 个 Span + 10 次指标
   ≈ 28µs，占 **5.6%**。这个比例可以接受，全量开启也没有压力

## 复现

```bash
pnpm bench v0.8.0 --iterations=20000 --report
```

## 已知限制

- 测的是纯埋点开销，不含网络上报（真实 Exporter 是异步批量的，不在请求路径上）
- 采样率对成本的影响是线性的，未单独测 1% / 10%
- 序列化的成本与"序列数"成正比：**标签基数爆炸会同时打爆内存和抓取耗时**
