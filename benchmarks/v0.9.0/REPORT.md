# v0.9.0 Benchmark 报告 —— 分布式原语的成本

生成时间：见 `results.json`（`--iterations=20000`）。

## 结果

| 操作 | 单次开销 | 吞吐 | p95 |
| --- | --- | --- | --- |
| Snowflake → bigint | 0.61 µs | 1,648,381 ops/sec | 0.72 µs |
| Snowflake → string | 0.55 µs | 1,817,492 ops/sec | 0.56 µs |
| 加锁 + 释放（无竞争） | 3.70 µs | 270,029 ops/sec | 5.86 µs |
| 事件发布（2 个订阅者） | 2.64 µs | 378,494 ops/sec | 3.25 µs |

## 怎么读

1. **ID 生成 0.61µs，比 v0.8.0 起一个 Span（5.84µs）还便宜 10 倍** ——
   所以"每条写路径都发一个 Snowflake ID"完全不值得省。
   反过来说：既然这么便宜，就没有理由再用自增主键了

2. **加锁 3.7µs** —— 对比 v0.7.0 的令牌桶（0.22µs）贵 17 倍，
   但对比一次数据库写（几百 µs 起）完全可以忽略。
   **结论：判断"要不要加锁"时，成本不是理由；只有正确性才是理由**

3. **事件发布 2.64µs（2 个订阅者）** —— 开销随订阅者数量线性增长。
   所以事件总线适合"少量重要事件"，不适合当高频管道用
   （那种场景该用直接的流式处理）

4. 一个真实订单请求（发 ID + 加锁 + 发布事件 ≈ 7µs）
   只占 v0.2.0 测得的 HTTP 全链路（500µs）的 **1.4%**

## 复现

```bash
pnpm bench v0.9.0 --iterations=20000 --report
```

## 已知限制

- 锁测的是**无竞争**路径：有竞争时开销主要是等待时间，与实现无关
- 事件总线测的是同步订阅者；异步订阅者的开销取决于订阅者自身
- 所有数字都是进程内的；换成 Redis / MQ 后端后是网络开销主导
