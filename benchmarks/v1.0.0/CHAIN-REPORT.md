# v1.0.0 全链路压测报告 —— 一次请求穿过的所有层

## 链路

```
fetch → rest 网关（路由 / 中间件 / 参数绑定 / 统一响应）
      → rpc.call（连接池 / JSON 编解码 / 4 字节分帧）
      → rpc 服务端（收帧 / 找方法 / 调用）
      → 业务（@nofault/cache getOrSet）→ 内存存储
```

两个进程 + 一个压测客户端同机（macOS，Node ≥ 20），无人工延迟——量的是**框架开销的真实叠加**。

## 结果（`--n=2000 --conc=16`）

| 路径 | 吞吐 | mean | p50 | p95 | p99 |
| --- | --- | --- | --- | --- | --- |
| 热读（缓存命中） | 1,549 ops/s | 10.30ms | 8.32ms | 15.73ms | 59.61ms |
| 冷读（穿透到存储） | 2,325 ops/s | 6.86ms | 6.26ms | 11.78ms | 16.95ms |
| 写（POST） | 1,589 ops/s | 10.05ms | 9.25ms | 15.53ms | 21.00ms |

## 怎么读这些数字

**冷读为什么比热读还快？** 热读的 p99（59.61ms）暴露了答案：前几个并发请求在同一 key 上
触发 getOrSet 的**单飞合并**（防击穿），先到的请求等后到的加载完成——这是**故意的正确性换延迟**：
合并省掉的是 N 倍存储压力。单飞过后热读稳定在 p50 ≈ 8ms。这提示生产部署要在**上线预热**热点 key。

**写比冷读慢**：POST 走 bodyParser（解析 JSON）+ 无缓存兜底的完整调用链，多出的 ~3ms
主要是 body 解析与响应包裹。

**单进程自压测的口径**：客户端、网关、后端共享同一台机器，CPU 会互相挤占——
绝对吞吐比生产低；但三条路径的**相对关系**（冷读≈热读、写略慢）与 p95/p99 的形态是可信的。

## 复现

```bash
pnpm build
node benchmarks/v1.0.0/chain-bench.mjs --n=2000 --conc=16
```

## 已知限制

- 存储是内存 Map：真实 SQL 数据源会增加 1~10ms 量级，框架开销占比随之下降
- 未压 SSE / 流式 RPC：流式语义下"吞吐"由服务端产出节奏决定，指标形态完全不同，需要单独设计
