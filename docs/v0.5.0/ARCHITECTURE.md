# v0.5.0 架构：数据访问层

> 图见 [`ARCHITECTURE.svg`](./ARCHITECTURE.svg)

## 一句话

**方言只生成字符串，Repository 不碰 SQL，DataSource 是唯一的 IO 边界。**
于是 ORM 可以不装数据库就跑起来，也能接任何驱动。

## 一、分层

```
@Entity 装饰器 ──> EntityMeta（元数据）
                        │
Repository / QueryBuilder ──> Dialect ──> SQL 字符串 + 参数 ──> Executor（驱动）
        │
        └──> DataSource（IO 边界）
                 ├─ MemoryDataSource（内存表 + 迷你 SQL 引擎）
                 └─ SqlDataSource（executor 回调，不绑驱动）
```

两条纪律：

1. **Dialect 不做 IO** —— 所以 SQL 可以单测，换驱动只要换 executor
2. **Repository 不写 SQL** —— 业务逻辑与数据库方言彻底解耦

## 二、为什么自带内存数据源

- 示例、测试、CI **不该依赖外部数据库**
- 事务语义（快照 + 回滚）在内存里能完整实现，行为与真实事务一致
- 迁移需要一张 `schema_migrations` 表；为此内存数据源内置了一个**迷你 SQL 引擎**，
  只支持迁移真正用到的几条语句（CREATE / DROP / INSERT / SELECT / UPDATE / DELETE），
  超出即抛错——宁可明确失败，也不假装支持

## 三、刻意不做的事

| 不做 | 理由 |
| --- | --- |
| 脏检查 / 自动 flush | "什么时候落库"必须在代码上一眼可见；隐式写库是最难排查的一类问题 |
| 关联懒加载代理 | 魔法越多，越难预判一次调用会打几条 SQL |
| 级联保存 | 显式 `save()` 已经覆盖绝大多数场景，猜错的代价太大 |
| 从契约猜关联 | 生成器对嵌套/数组一律存 JSON，不猜外键 |

## 四、事务

- 抛错即回滚，快照在最外层建立（嵌套共享同一回滚点）
- **快照必须包含 raw 写入的表**：否则迁移失败时版本号已落库、结构却回滚了，
  下次永远不会重试——这是本次实现里最容易写错的一处
- 每个迁移**各自一个事务**：已提交的不回退，失败的也不记版本号

## 五、缓存的三个经典问题

| 问题 | 应对 | 位置 |
| --- | --- | --- |
| 击穿（同 key 并发） | single-flight：同 key 只回源一次 | `getOrSet` 的 `inflight` 表 |
| 穿透（查不存在的数据） | 可选缓存空值，默认关闭 | `cacheNullValue` |
| 雪崩（同批 key 集体过期） | TTL 加 ±10% 抖动 | `withJitter` |

`getOrSet` 是**唯一推荐**的用法：手写"get → 未命中 → 查库 → set"这三步，
在并发下必然踩坑，把它收进实现里，业务代码就写不出错的写法。

另外两条容易被忽略的语义：

- loader 返回 `undefined` 时**不写缓存**（固化"查不到"会让数据写入后永远读不到）
- loader 抛错会向所有等待者传播，且**不留下锁**（否则后续请求永远拿不到数据）

## 六、生成器扩展

`--with-orm` 额外产出 `data/entities/*.entity.ts` 与 `data/repositories/*.repository.ts`。

两条规则很关键：

1. **只为"被当作响应类型用过"的类型建表**。请求 DTO 是传输对象，给它建表毫无意义
2. **契约里的 `id` 字段要跳过**：主键由生成器统一提供，否则生成两个同名的 `id`

骨架只给三件套（`findById` / `paginate` / `create`），业务查询由人接管——
删掉首行生成标记即宣告接管，此后再生成也不会覆盖。

## 七、本版踩到的坑

1. **自增主键上的 `0` 是占位，不是值** —— TS 里 `new User().id` 恒为 0，
   照原样写入会让所有记录撞主键。现在 `save()` 会把 0 当作"未设置"
2. **布尔在库里是 1/0，实体上是 true/false** —— 比较前必须归一化，
   否则"能存进去却查不出来"（极难察觉）
3. **事务回滚要覆盖 raw 表** —— 见上
4. **生成的模块不知道手写的 DataModule** —— 模块装配注定由人做，
   所以 `user.module.ts` 通常是第一个被接管的生成物

## 八、已知限制

- SQL 方言只覆盖单表 CRUD，无 JOIN（多表请用 raw 或自己在 repository 里写）
- 内存数据源的 WHERE 只支持迁移用到的简单形式
- LRU 淘汰是 O(n log n) 排序，`max` 设很大时会痛
- 无连接池（交给驱动 / executor）
