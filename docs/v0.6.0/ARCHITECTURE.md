# v0.6.0 架构：RPC 框架

## 一句话

**TCP 是字节流，没有消息边界**——所以自己分帧；
**一条连接上可以同时有多个在途调用**——所以每个请求要有 id。

这两条决定了 RPC 协议的全部设计。

## 一、协议：4 字节长度 + JSON

```
[ 4 字节大端长度 ][ JSON body ]
```

不分帧的后果是"偶发的 JSON 解析失败"，而且**只在负载稍大时才复现**。
长度前缀还顺带带来两个好处：读满整帧前就知道要分配多少内存，
以及可以挡住超大帧打爆内存（`maxFrameBytes`，超限直接丢缓冲并报错）。

## 二、请求必须带 id

同一连接上并发多个调用时，响应**顺序不保证**与请求一致（后端耗时不同）。
所以响应带 `id`，客户端按 id 配对。
没有 id 的后果只有两种：要么一条连接只能串行，要么响应配错对象。

## 三、四个可独立开关的机制

| 机制 | 应对 | 关掉会怎样 |
| --- | --- | --- |
| 连接池 | 握手成本（实测 3.1×） | 每次调用都握手 |
| 超时 | 上游慢 | 一个慢调用拖死整个调用方 |
| 重试 | 瞬时故障 | 偶发抖动直接报错 |
| 注册发现 | 实例变更 | 往已下线的实例发请求 |

**重试只对"可能成功"的失败生效**：网络错误、超时、解析错误。
业务错误（方法不存在、用户不存在）重试毫无意义，只会放大故障。

## 四、注册发现

- 接口只有 5 个方法：register / deregister / heartbeat / discover / list
- 内存实现开箱可用；背后可以换成 etcd / consul / nacos / k8s service
- **TTL 过期自动剔除**：进程被 SIGKILL 时没机会注销自己，不下线就会被一直调用

负载均衡用**加权轮询**而不是随机：随机在短窗口内会把流量打偏（热点），
轮询在任何窗口内都更均匀。

## 五、拦截器

与 HTTP 中间件同构，区别只是签名里带 `ctx`——
RPC 需要知道"现在调的是哪个方法"，才能做按方法的限流、审计、埋点。

ctx 在**组合时传入**（不是模块级变量）：
同一个 server 上会有多个并发调用在飞，全局"当前上下文"必然串号。

## 六、错误码 → HTTP

`rpcErrorToStatus()` 给出唯一一份映射：

| RPC | HTTP | 理由 |
| --- | --- | --- |
| TIMEOUT | **504** | 504 才是"上游超时"，502 是"收到无效响应" |
| UNREACHABLE / PARSE | 502 | 上游不可用或响应不可解析 |
| METHOD_NOT_FOUND | 404 | 调用方写错了方法名 |
| 业务码 4xx/5xx | 原样 | 码是契约，框架不该吃掉 |

每个网关都手写一遍映射，结果就是"同一个超时，有的 500、有的 502"。

## 七、本版踩到的坑

1. **并发首调各建一条连接** —— 三个并发调用同时发现"池是空的"，
   池化在最需要它的那一刻失效。修法：按 `host:port` 去重在建连接
2. **拦截器 ctx 不能靠模块级变量取** —— 并发下必然串号
3. **Handler 允许同步返回** —— 组合时统一 `Promise.resolve()` 包一层
4. **装饰器里引用后面才定义的 const** —— 会踩暂时性死区（TDZ）

## 八、已知限制

- 只有 JSON 编解码（可换 Codec）
- 无限流 / 熔断 → v0.7.0
- 无链路追踪上报 → v0.8.0
