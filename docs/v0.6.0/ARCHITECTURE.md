# v0.6.0 架构：RPC 框架

## 一句话

**TCP 是字节流，没有消息边界**——所以自己分帧；
**一条连接上可以同时有多个在途调用**——所以每个请求要有 id。

这两条决定了 RPC 协议的全部设计。

## 一、协议：4 字节长度 + JSON

```
[ 4 字节大端长度 ][ JSON body ]
```

不分帧的后果是"偶发的 JSON 解析失败"，而且**只在负载稍大时才复现**。
长度前缀还顺带带来两个好处：读满整帧前就知道要分配多少内存，
以及可以挡住超大帧打爆内存（`maxFrameBytes`，超限直接丢缓冲并报错）。

## 二、请求必须带 id

同一连接上并发多个调用时，响应**顺序不保证**与请求一致（后端耗时不同）。
所以响应带 `id`，客户端按 id 配对。
没有 id 的后果只有两种：要么一条连接只能串行，要么响应配错对象。

## 三、四个可独立开关的机制

| 机制 | 应对 | 关掉会怎样 |
| --- | --- | --- |
| 连接池 | 握手成本（实测 3.1×） | 每次调用都握手 |
| 超时 | 上游慢 | 一个慢调用拖死整个调用方 |
| 重试 | 瞬时故障 | 偶发抖动直接报错 |
| 注册发现 | 实例变更 | 往已下线的实例发请求 |

**重试只对"可能成功"的失败生效**：网络错误、超时、解析错误。
业务错误（方法不存在、用户不存在）重试毫无意义，只会放大故障。

## 四、注册发现

- 接口只有 5 个方法：register / deregister / heartbeat / discover / list
- 内存实现开箱可用；背后可以换成 etcd / consul / nacos / k8s service
