# v0.7.0 架构：服务治理

## 一句话

**限流挡流量、熔断别再打坏掉的下游、舱壁限制并发、退避把重试打散**——
四件事互不替代，缺一个就会在特定故障模式下裸奔。

## 一、四件套各管什么

| 原语 | 问题 | 不做的后果 |
| --- | --- | --- |
| 令牌桶限流 | 进来的人太多 | 突发流量把服务打垮 |
| 熔断器 | 下游已经坏了 | 每个请求都等超时，拖死调用方 |
| 舱壁 | 一个慢依赖吃光并发 | 慢依赖拖垮**所有**接口 |
| 退避重试 | 重试风暴 | 刚恢复的服务被重试流量再打挂 |

## 二、为什么是令牌桶而不是固定窗口

固定窗口在**窗口切换的瞬间**会放过 2 倍流量（窗口末尾打满 + 窗口开头打满）。
令牌桶按速率匀速补充，没有这个尖峰。

配置里有两个参数，含义完全不同：

- `capacity`：**能攒多少**（允许的突发量）
- `refillPerSecond`：**每秒给多少**（长期速率）

把这两个搞混是最常见的限流配置错误。

## 三、熔断的三个状态

```
CLOSED ──(连续失败达阈值)──> OPEN ──(冷却结束)──> HALF_OPEN ──(探针成功)──> CLOSED
                              ↑                        │
                              └──────(探针失败)────────┘
```

两个最容易写错的地方：

1. **OPEN 期间绝不能再打下游**。一边"熔断"一边继续发请求，等于没熔断
2. **HALF_OPEN 只允许有限个探针**（`halfOpenMaxCalls`）。
   不限流的话，冷却结束的瞬间全部流量会一起涌向刚恢复的下游，直接再打挂

另外：`isFailure` 允许把"业务校验失败"排除在外——
参数错误不是依赖故障，不该触发熔断。

## 四、舱壁

思路来自造船：把船舱隔成多个密闭空间，进水也不会整船沉没。
对应到服务：**每个依赖一个并发上限**，某个依赖慢住时只耗尽自己的配额。

队列必须**有界**（`queueLimit`）：无界队列只是把"立即失败"变成"稍后一起失败"，
而且会吃光内存。

## 五、退避为什么必须抖动

所有调用方**同时**重试 = 重试风暴，会把刚恢复的服务再打挂。
抖动（默认 ±50%）把重试时间打散——
这是分布式系统里最便宜也最有效的保护。

## 六、中间件的顺序

```
限流（最外层）→ 舱壁 → 熔断（最内层）
```

顺序反了就会"被限流的请求也占着舱壁配额"，白白浪费资源。

## 七、本版踩到的坑

1. **熔断打开时返回 500 而不是 503** —— `CircuitOpenError` 不是 HttpException，
   框架不认识就一律按 500 处理。控制器必须显式翻译它
2. **限流桶在测试间共享** —— 后面的用例一上来就被 429。
   按 `x-forwarded-for` 隔离即可
3. **熔断必须能被主动验证** —— 示例里加了 `/faulty/break?mode=down` 开关，
   否则只能靠等线上出事

## 八、已知限制

- 限流是**单进程**的，多实例部署时需要外部存储（Redis）才能全局限流
- 熔断状态也在进程内，不跨实例共享
- 无自适应限流（根据下游延迟动态调整）
