# v0.9.0 架构：微服务全家桶

## 一句话

前八个版本交付的是**能力**；这一版负责把它们**接起来**，
并补上微服务必需、但单进程时代可以糊弄过去的四样东西。

## 一、为什么这四样不能省

| 缺了它 | 后果 | 什么时候被发现 |
| --- | --- | --- |
| 分布式 ID | 多实例各有自增计数器，合表必撞 | 上线当天 |
| 分布式锁 | 定时任务在 N 个实例上跑 N 遍；用户连点两次被扣两次 | 上线一周后 |
| 事件总线 | 模块之间直接互相 import，最后变成一坨 | 三个月后没人敢改 |
| 一键装配 | 五十行样板代码，顺序错了就有微妙问题 | 偶发生><生产故障时 |

## 二、Snowflake

```
0 | 41 位毫秒时间戳 | 5 位数据中心 | 5 位机器 | 12 位序列号
```

**为什么不用自增主键**：多实例各有各的计数器。
**为什么不用 UUID**：无序。无序主键让 B+ 树的插入退化成随机写，
数据量一大写入性能掉一个数量级。

两个必须做对的细节：

1. **时钟回拨** —— 服务器对时会往回调。不处理就会发出重复 ID，
   而 ID 重复是"三个月后某个对账任务炸掉"级别的问题
2. **序列号耗尽** —— 同一毫秒超过 4096 个请求时必须**等到下一毫秒**，
   不能回绕。回绕同样产生重复 ID

返回类型是 `bigint` / **字符串**而不是 `number`：
63 位远超 `Number.MAX_SAFE_INTEGER`（53 位），
转成 number 后末尾几位会被静默抹掉——两个不同的 ID 会变成同一个。

## 三、分布式锁

**释放时必须校验 token**，这是全部关键：

```
服务 A 持锁 → GC 停顿导致超时 → 锁被 B 拿走
  → A 恢复过来 → 释放锁
  → 释放的其实是 B 的锁 → C 立刻又拿到 → A 和 C 同时进入临界区
```

而这恰恰是"加锁本来要防止的事"。

其他两点：

- **自动续期（watchdog）** 默认开。执行时间不可控时必须续期，
  否则跑一半锁就过期了。续期失败要**停掉** watchdog——
  那把锁已经不是自己的了
- **`run()` 用 finally 释放**。忘了释放的锁会挂到 TTL 到期，
  这段时间整个功能都是停的

后端可插拔：`MemoryLockBackend` 用于单进程与测试，
换成 Redis 只要实现三个方法（SET NX PX / Lua 释放 / Lua 续期）。

## 四、调度器

最容易写错的两处，默认值都选了**保守**的那一侧：

| 选项 | 默认 | 理由 |
| --- | --- | --- |
| 错过执行要不要补跑 | **不补** | 补的话重启瞬间会涌入几十个任务，把刚起来的服务再打挂 |
| 上一轮没跑完能否起下一轮 | **不能** | 允许重叠的话一个慢任务会越积越多，变成事实上的自我 DoS |

另外提供两种固定周期：

- `every(ms)` —— 从**开始**时刻起算，节奏稳定
- `fixedDelay(ms)` —— 从**结束**时刻起算，任务慢了也不会堆积

cron 解析器有一条容易记错：**日与周是"或"关系**
（与 Unix cron 一致）。实现成"与"，`0 0 1 * 0` 永远不会触发。

## 五、事件总线

三条纪律：

1. **一个订阅者抛错不影响其他订阅者** —— 否则某个模块的 bug
   会让整条事件链断了，而且没人知道为什么
2. **异常不能被静默吞掉** —— 交给 `onError`。吞掉的话事件
   "看起来发出去了，什么都没发生"，是最难查的一类 bug
3. **默认并行；需要顺序时 `sequential: true`** ——
   并行下多个订阅者同时改同一份数据会互相覆盖

`subscribe()` 返回**退订函数**：忘记退订是事件总线最常见的内存泄漏来源。

## 六、一键装配：顺序就是全部

```
启动：迁移 → 订阅事件 → 起 HTTP 监听 → 起定时任务 → 置就绪
停机：停定时任务 → 关监听 → 释放数据源   （逆序）
```

三条理由：

- **先迁移再接流量** —— 否则半初始化的实例就开始处理请求
- **先关监听再注销** —— 反过来会有一段时间"已下线但还有请求进来"
- **就绪标记最后打开** —— 在那之前探针必须如实回答"还不能服务"
  （否则 readinessProbe 形同虚设）

**启动失败要回滚**: teardown 掉已经建好的连接池与监听器，
留着就是泄漏。

## 七、本版踩到的坑

1. **注释里写了 `*/n`，把块注释提前闭合了** ——
   后面的代码全变成裸标识符，报了一片 TS1005
2. **序列号耗尽时回绕而不是等待** —— 注释里写着"必须等下一毫秒"，
   实现却直接绕回去复用序列号，产出重复 ID。是测试发现的：
   请求 5000 个只拿到 4096 个唯一的
3. **`Error` 子类不能用 `name` 做构造参数** —— 覆盖了基类的 `name`，
   TS 要求显式 `override`
4. **示例里一开始有两套 EventBus** —— DI 容器里 `useValue` 新建了一份，
   `main.ts` 又建了一份，结果订阅的和发布的是两个不同实例，事件一个都收不到。
   共享的东西必须在容器外提出来单例

## 八、已知限制

- 锁与事件总线都是**进程内**的，跨实例需要 Redis / MQ 后端
- 调度器无持久化，进程重启后定时任务的进度会丢
- 无选举（leader election），"只跑一次"依赖分布式锁而非选主
