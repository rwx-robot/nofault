# v1.0.0 架构：认证与授权

## 一句话

**安全相关的默认值一律选"拒绝"那一侧**——漏写一个装饰器应当是"调不通"，
而不是"谁都能调"。

## 一、JWT：三条不能写错的地方

1. **`alg` 必须从服务端配置取，不能从 token 里读**。
   "alg: none" 与 RS256→HS256 混淆攻击，根源都是
   "照着 token 头里说的算法去验证"。这里根本不读 header 决定算法，
   只确认它就是我们期望的那个

2. **过期必须校验，且允许少量时钟偏移（默认 30 秒）**。
   不校验 exp，token 永不失效；不容忍偏移，
   签发方与校验方差几秒就会大面积误判

3. **比较签名用 `timingSafeEqual`**。
   `===` 在第一个不同字节就返回，理论上是可被利用的信息泄漏

另外：token 无效时**不区分原因**，一律 401。
告诉调用方"签名不对"还是"过期了"都是在给攻击者递信息。

## 二、密码：三条铁律

1. 用**故意慢**的 KDF（scrypt），不用通用哈希
2. **每次新盐**。盐相同 → 相同密码哈希相同 → 拖库后能看出谁用了同一个密码
3. 定时安全比较

哈希格式 `scrypt$N$r$p$salt$hash` 把**参数写进结果**：
以后调高成本时，老哈希仍能验证。否则一改 COST，
所有老用户都登录不了，只能强制重置。

## 三、RBAC：默认是拒绝

```
@Public()      → 谁都能调
（无标记）      → 需要登录
@Roles('admin') → 需要该角色
```

`@Roles` 的语义是**任一**（OR）而不是全部（AND）：
多角色通常表达"管理员或审计员都能看"，
要求全部反而会让多角色用户越权失败。

## 四、中间件只提供身份，不做授权

`authMiddleware` 的职责止于"把身份放进请求上下文"，
授权判断交给 `authorize()`。

混在一起的结果是"鉴权逻辑散落在中间件里"，
没人知道某个接口到底是怎么被保护的。

### 顺序：先问是不是 @Public，再决定要不要 401

这个顺序写反了，公开接口（`/health`、`/login`）会被一起拦掉——
**健康检查挂了会触发误摘除，是生产事故级别的**。
（第一版就是这么错的，集成测试抓出来的。）

## 五、已知限制

- 只有 HS256（对称密钥），无 RS256 / JWKS
- 无 refresh token 与吊销机制（JWT 无状态的代价）
- 未内置 CSRF / CORS 细粒度策略
- 日志与 trace 未自动关联（traceId 可拿，要自己写进日志）
